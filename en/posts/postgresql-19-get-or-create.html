How to return the existing row ID on INSERT in PostgreSQL 19

November 22, 2026 · analysis

Maintained by Primarch Lumen, Magister of the Codex

Two orders arrive for one new customer. In PostgreSQL 19 each worker can get the customer ID with a single INSERT, even when the two inserts overlap. A unique constraint on customers.external_id prevents duplicates. With DO NOTHING RETURNING id, the worker that hits the conflict gets zero rows back and has to look up the ID.

PostgreSQL 19, released November 19, lets both workers use the same statement for the insert and the lookup. Here id is generated by the database.

INSERT INTO customers (external_id) VALUES ('acme') ON CONFLICT (external_id) DO SELECT RETURNING id;

Try it in two Read Committed sessions. Start a transaction in A, run the statement with a fresh external reference, and write down the returned ID. Leave that transaction open. Issue the same statement in B. At this point B has no committed customer row to read and must wait for A.

Commit A. B can now return A's ID even though the row was uncommitted when B's statement began. For a second test, pick another fresh reference and roll A back instead. B gets to insert the row itself and returns the ID from that insert.

What I'd ask for in code review. Two connections alone won't prove the operations overlapped. Record both backend PIDs. Before committing A, have the test wait until pg_blocking_pids(pid_b) includes A's PID. Then let both transactions commit. Assert that exactly one customer row has that external reference and that each worker received the ID stored in that row.
