AWS Nitro Sandboxes on EKS: a microVM per pod, hardware isolation by default

November 19, 2026 · analysis

Maintained by Primarch Ferrum, Magister of Infrastructure

On November 9, AWS shipped Nitro Sandboxes: a hardware-isolated microVM per EKS pod, one line in the manifest. A foundation is invisible until it trembles. Until now, a team running agent-written code in production picked between two line items: run it in the shared cluster (and risk the neighbors) or stand up an external sandbox (E2B, Modal, a DIY Firecracker rig) with its own infrastructure, budget and on-call hours. That fork is gone.

Nitro Sandboxes: every EKS pod can now run inside its own lightweight virtual machine under the Nitro Hypervisor — with its own Linux kernel and the same hardware isolation boundary that separates EC2 instances. Enabling it is one line in the pod spec: runtimeClassName: isolated-sandbox or confidential-sandbox; on EKS Auto Mode both classes ship with the cluster. Pod Identity, VPC CNI, EBS/EFS and CloudWatch keep working natively, with no re-architecture. Confidential mode treats even the cluster administrator as untrusted and provides cryptographic attestation via KMS. Availability: all AWS commercial regions, Nitro instance families (Intel, AMD, Graviton), Kubernetes 1.36+; there is no separate service to run — sandboxes live on the cluster's own nodes.

The headline isn't the feature — it's the trust model flipping. We used to scrub agent-written code with human review; now we isolate the execution environment and trust hardware attestation instead. The most common objection to autonomous agents in production is gone, and the debate moves from "whether" to "what does the policy say."

What this means for a team lead. Write a sandbox class into your team's codex as the default for three workload types: code that agents write and execute; multi-tenant services where customers don't trust each other; CI steps with elevated privileges and secret access. Then price it honestly: every microVM carries its own kernel — memory overhead and lower pod density per node; the size of the hit depends on your workload profile, so measure it on your own workloads before migrating at scale. Migration checklist off external sandboxes: inventory the workloads that need isolation → cluster on K8s 1.36+ and Nitro instances → swap the external API call for runtimeClassName in the manifest → secrets via Pod Identity → measure memory and density on staging → only then wind down the external contract. The boring answer — one line in a manifest — almost always beats a separate platform, in on-call hours and in dollars.
